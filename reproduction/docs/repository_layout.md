# 仓库边界、历史与同步

更新：2026-10-02。

## 为什么保留 reproduction

名称虽源于“复现”，内容已经是安装式 Python 包。已有 `src/`、`configs/`、`tests/`、`scripts/` 分工合理。真正的问题是入口混乱、论文材料混入、历史与当前口径混淆，而不是目录不够时髦。

服务器的 `reproduction/data`、`runs`、`outputs`、`checkpoints` 是用户数据目录的软链接，多个脚本和冻结配置也依赖现有路径。因此这次保留路径，不为改名承担可追溯性风险。后续新接口经测试稳定后再考虑整体迁移，旧版本必须仍能运行。

## 三种存储职责

| 位置 | 保存内容 | 本次处理原则 |
|---|---|---|
| 本机毕设目录 | 代码、文献、论文、个人笔记、汇报表格 | 非代码材料留在原处，由根目录忽略规则隔离 |
| GitHub 当前分支 | 源码、配置、测试、研究规格、少量历史证据 | 取消非代码论文材料跟踪，不改写历史 |
| 服务器代码目录 | 同一 Git 版本及数据软链接 | 工作区干净时快进更新；旧论文材料先备份 |
| 服务器数据/结果目录 | 数据池、模型、运行输出 | 不移动、不清理、不重算、不改权限 |

根目录采用显式白名单：README、CHANGELOG、Git 配置和 `reproduction/`。若未来新增发布目录，需要显式更新规则；不要对整个毕设目录执行强制添加。

## 备份与恢复

本机本次操作前的完整 Git bundle、无 textconv 的二进制工作区补丁，以及用户已修改的 Excel、图文件副本保存在：`E:/毕设/local-archive/repo-cleanup-20261002/`。bundle 保存已提交历史，补丁保存受跟踪文件的未提交差异；原有未跟踪论文目录仍在本机原位置，不声称它们已包含在 bundle 中。

本次整理不提交用户原先修改的 `finding_1_detection_transfer.png`。根目录 Excel 退出 Git 后也保留本地最新版，不回滚为远程版本。已经在本地移动的暑期材料不被恢复或重写。

服务器备份位置及部署版本以本次交付记录为准。只在账号自己的项目/归档路径工作；不用 `reset --hard`、强推或清理忽略文件。

## 当前和后续分界

现在可用：历史正式配置、分片执行、既有检测/量化/估值接口和测试。

现在未实现：探索计划中的新配对对照、逐样本预测缓存、细化效用指标和统一第三方插件契约。计划不等于功能上线。

建议后续按实际功能新增 `evaluation`（独立重评分）、`policies`（治理动作）、`artifacts`（逐样本缓存契约）等模块；不要先建立大量空目录，再称为 benchmark。
