# 正式实验资源感知调度器部署记录

## 部署结论

2026-08-12 已在课题组单张 NVIDIA L40 共享服务器上部署“后台托管 + CPU/GPU 流水线”调度方式。该改动只调整分片执行次序与资源分配，不改变冻结的正式配置、数据池、协议、检测器、量化器、随机种子、bag 或统计规则。

服务器资源为单张 46,068 MiB L40、64 个 CPU 逻辑核和 251 GiB 内存。既有深度分片训练期间 GPU 利用率通常达到 70%--95%，因此没有采用两个深度模型同卡并行；调度器保持任一时刻最多一个深度分片，同时使用 CPU 余量运行经典检测器。

## 隔离与恢复机制

- seed 2027 被确定性拆分为 8 个 CPU 分片和 14 个 GPU 分片，集合无交集且合计 22 个；
- CPU 分片显式使用 `execution_device=cpu` 并隐藏 CUDA；深度分片仍强制使用 CUDA；
- 完整正式配置仍须通过五种子、P1--P4、100 bags、方法注册表和 CUDA 预检；CPU 覆盖只允许单个经典派生分片，不能用于深度方法；
- 全局调度锁阻止传统入口和资源感知入口重叠，CPU 独立锁防止经典队列重复启动；
- 分片计划改为原子发布，完成标记仍最后写入；
- 发现外部 GPU 进程时只停止本项目当前 GPU 子进程并等待，不删除、暂停或修改其他用户进程；
- 后台任务不依赖 SSH 会话，网络中断后仍持续运行。

## 验证结果

服务器正式 Conda 环境中的相关测试共 13 项全部通过。使用已完成的 seed 2026 进行零工作量端到端测试时，CPU/GPU 待运行队列均为 0，没有重复运行分片，调度器正常发布状态并退出。

seed 2027 后台任务启动后重新登录服务器检查，CPU 队列正在运行 `s2027__P1__char3gram`，约占用 2.7 个 CPU 核且没有 CUDA 进程；GPU 队列正在运行 `s2027__P1__flat_transformer`，GPU 利用率约 94%、显存约 1.8 GiB。GPU 上只有该受控深度进程，两队列选择的分片互斥，后台任务已通过断线存活验证。

首次启动时，旧版 CPU 子队列因正式预检仍要求 CUDA 而在训练前安全退出，没有发布错误完成标记。随后增加了仅限经典派生分片的 CPU 执行覆盖及测试，并以独立 CPU 锁恢复经典队列；原 GPU 队列未中断。该事件不改变任何正式实验结果。

## 后续约束

seed 2027 完成后必须先验收 22 个分片的行数、重复键、量化器状态、正式纳入资格和资源日志。确认与 seed 2026 的证据契约一致后，才可用相同后台策略依次运行 seed 2028--2030。禁止为了提高速度在同一张共享卡上并行运行多个深度模型。
